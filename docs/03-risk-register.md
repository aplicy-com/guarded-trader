# 03 — Risk Register

Living document. Reviewed at every phase gate (`07-roadmap.md`) and after
any incident. **Likelihood** and **Impact** are rated Low/Medium/High at
the $100-principal, Phase 1–4 scale — re-rate if principal or scope ever
changes. **Owner** is a role, currently all held by the operator,
except where the automated system is the enforcing owner.

Status legend: **Open** — mitigation planned/partial, not yet verified.
**Mitigated** — control designed and specified here; implementation lands
in the phase noted. **Accepted** — residual risk knowingly carried.

## Market risk

| ID | Risk | Likelihood | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|
| M1 | Sudden adverse price move (flash crash, news shock) exceeds the stop-loss's assumed slippage, causing a fill far worse than modelled. | Medium | High | ATR-based stop sizing (not fixed %); max-drawdown hard halt (R4); avoid illiquid/low-cap pairs; documented in `06-runbooks/nuclear-protocol.md` for the "exchange anomaly" case. | Risk engine (Freqtrade) / Conductor | Mitigated (design) — implemented Phase 2 |
| M2 | Low liquidity in a traded pair causes slippage well beyond backtest assumptions. | Medium | Medium | Restrict to BTC/ETH and other high-24h-volume majors only (low-frequency ADR-0005); minimum volume filter in pair whitelist. | Strategy design | Mitigated (design) |
| M3 | Correlation risk — BTC and ETH (and most alts) move together, so nominal "2–3 positions" can be one effective bet. | High | Medium | Correlation guard treats BTC/ETH (and any pair with rolling correlation above a threshold — TBD (Phase 3) exact threshold) as a single exposure unit for position-count and risk-budget purposes. | Conductor | Mitigated (design) |
| M4 | At $100, exchange fees erode any edge smaller than the round-trip cost (~0.5% taker on Kraken). | High | High | Maker-preferred order placement; strategies must model conservative fees/slippage in backtest; minimum expected edge threshold (~0.7%/trade) before a strategy is considered; low-turnover-only strategies (research review §5). | Strategy design / Research loop | Mitigated (design) |
| M5 | Regime change — a strategy validated in one market regime (e.g. trending) fails when conditions shift (e.g. chop, high-vol bear). | High | Medium | Anchored + rolling walk-forward validation before promotion; scheduled re-validation every 4–6 weeks; reject/demote on OOS Sharpe collapse (NFR5). | Research loop | Mitigated (design) — implemented Phase 3 |
| M6 | Stablecoin or quote-asset de-peg / failure affects the value or liquidity of held balances. | Low | High | Prefer well-established quote assets; principal is small enough ($100) that total loss is bounded; monitor exchange notices. | Operator | Accepted |
| M7 | Pre-existing personal holdings in the same Kraken account (bought before the project, gifted, or otherwise not system-acquired) get sized into `max_deployed_capital` as if they were working profit, or get sold by a strategy that has no way of knowing they weren't the bot's to trade. | Medium | High | R5 (account isolation): capital sizing counts only ledger-recorded, system-bought balances; startup check aborts and alerts if a whitelisted pair holds an unexplained balance, rather than silently absorbing or trading it. | Conductor | Mitigated (design) — implemented Phase 2 |
| M8 | The principal is funded in CAD (Interac e-Transfer) but traded entirely in USD-quoted pairs (`ADR-0008`) — the system carries incidental CAD/USD exchange-rate exposure on the principal itself, on top of the trading strategy's own exposure to the traded assets. | Low | Low | Principal is small ($100) which bounds absolute exposure; conversion happens once at funding time, not per-trade; NFR6's CAD-equivalent ledger valuation already tracks the CAD value of the account regardless, so the exposure is visible, not hidden. | Operator | Accepted — flagged during ADR-0008 (work package 2F); not separately mitigated beyond the small principal size |

|---|---|---|---|---|---|---|

## LLM / research-loop risk

| ID | Risk | Likelihood | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|
| L1 | LLM proposes a strategy with a logic bug (e.g. inverted signal, off-by-one on bar timing). | High | Medium | No LLM-authored strategy reaches capital without passing deterministic backtest, walk-forward, and unit tests first; a second LLM review pass is used as an additional (not sole) check. | Research loop / Operator | Mitigated (design) — implemented Phase 3 |
| L2 | LLM proposes an overfit strategy (curve-fit to historical backtest data). | High | High | ≤6 tunable parameters cap; anchored + rolling walk-forward; reject if OOS Sharpe < 50% of IS Sharpe (NFR5). | Research loop | Mitigated (design) |
| L3 | Non-determinism — the same prompt produces materially different strategy code/parameters run to run (observed directly in Alpha Arena S1.5). | High | Medium | Once a strategy is promoted, its code is pinned to a git commit hash and never silently re-generated; the live path never re-prompts the LLM mid-trade; every prompt/response is logged with a hash (NFR1). | Conductor | Mitigated (design) |
| L4 | Prompt injection via external data fed into the research loop (news headlines, on-chain data, social sentiment) attempts to alter the loop's behaviour or safety checks. | Medium | Medium | All fetched external content is treated as untrusted data, never as instructions, when composing prompts; safety/promotion-gate logic lives outside the LLM's control entirely (deterministic code, not a prompt instruction). | Conductor | Mitigated (design) — implemented Phase 3 |
| L5 | LLM API cost overrun from an unbounded or malfunctioning nightly research loop. | Medium | Low | Nightly token/spend budget with a hard cutoff; alert on overrun; exact budget TBD (Phase 3, research review §7.4). | Ops | Open — TBD (Phase 3) |
| L6 | LLM vendor outage or rate-limiting blocks a night's research loop. | Medium | Low | Research loop failure is non-blocking for live trading — the live path is 100% deterministic Freqtrade and does not depend on the LLM being reachable; loop retries the next scheduled run. | Conductor | Mitigated (design) |
| L7 | The nightly research loop's cumulative LLM API cost, over time, exceeds the $100 principal the system manages — the compute cost of running the experiment becomes larger than the capital at risk. | Medium | Low | R6 (research-loop cost ceiling): monthly budget with an 80% alert and a 100% hard stop; the hard stop pauses only the research loop, never trading (ADR-0003). Cost is tracked and reported honestly alongside trading results (`00-vision.md`), so this stays a visible trade-off rather than a hidden one. | Operator | Mitigated (design) — implemented Phase 3 |
| L8 | LLM-generated strategy code executes arbitrary Python inside the backtest/paper pipeline — a candidate could, in principle, read secrets from the environment, make outbound network calls, or write to disk, entirely independent of whether its trading logic is any good. Order-placement authority (ADR-0003) does not by itself constrain what the code is *capable of* before that boundary is ever reached. | Medium | High | Candidate code admission (ADR-0007): static analysis (import whitelist; `os`/`subprocess`/`socket`/`requests`/file-writes forbidden) before any execution; backtest/walk-forward run inside a throwaway, network-disabled sandbox with no exchange credentials, secrets, or ledger access; mandatory human `/approve` before any code version's first paper entry and every live allocation change. | Conductor | Mitigated (design) — implemented Phase 3 (re-tagged from "Phase 2/3": this is entirely Conductor/research-loop scope, which does not exist until Phase 3 — Phase 2's `Baseline4h` was hand-written, never LLM-generated, so this control has nothing to gate yet) |

## Security risk

| ID | Risk | Likelihood | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|
| S1 | Exchange API key or other secret leaks via the repo, logs, or a shared screen. | Medium | High | Secrets only in env vars / LastPass, never committed; `.gitignore` covers `.env` and key files; gitleaks pre-commit hook (`.pre-commit-config.yaml`); repo reviewed before any public push. | Operator | Mitigated (design) — implemented Phase 2 |
| S2 | Exchange API key is over-scoped (has withdrawal permission) by mistake. | Low | High | Key created with query + trade only, withdrawal explicitly disabled, IP-whitelisted; scope verified at creation and at every rotation (`06-runbooks/key-rotation.md`). | Operator | Mitigated (design) |
| S3 | Host (the Hetzner VPS from Phase 3; the Mac before that and as dev machine) is compromised via malware or an unpatched vulnerability. | Low | High | OS auto-updates enabled; no unnecessary exposed ports; remote access via Tailscale rather than public-facing ports (`04-architecture/security.md`); VPS: Hetzner firewall with zero inbound rules, key-only SSH, `fail2ban`, `unattended-upgrades`; minimal installed software on the trading host. | Ops | Mitigated (design) — implemented Phase 2 |
| S4 | Telegram bot token leaks, allowing an unauthorized party to issue control commands (including, in the worst case, attempting to disable safety controls). | Low | High | **Conductor's future bot** (Phase 3): token stored as a secret, never committed; chat/user ID allowlist enforced before executing any command; kill switch/flatten are the only destructive-adjacent commands and both only ever *reduce* risk, never increase it. **Freqtrade's own native bot** (enabled Phase 2D, `infra/README.md` "Telegram bot (status-only)"): verified directly against Freqtrade 2026.8 source that it has **no config-level per-command permission system** — `telegram.chat_id` gates *who* can reach the bot, not *which* commands they can then issue; `/forcebuy`/`/forceshort` are the only commands blocked server-side (`force_entry_enable: false`, confirmed live). Every other command (`/stop`, `/stopbuy`, `/forceexit`, `/delete`, `/reload_config`) remains reachable to whoever holds the token/chat_id, mitigated only by keeping those private and by every one of those commands being risk-neutral-or-reducing, never risk-increasing, at worst. | Ops (Freqtrade bot) / Conductor (future bot) | Mitigated (design) for Conductor's bot — implemented Phase 3; **partially mitigated only** for Freqtrade's native bot — token/chat_id secrecy is the real control, not a command-level block, since Freqtrade offers none |
| S5 | A dependency (PyPI package used by Freqtrade, Conductor, or CI) is compromised (supply-chain attack). | Low | Medium | Pinned versions with a lockfile; automated dependency-update alerts (Dependabot or equivalent); diffs reviewed before accepting an upgrade, especially for packages with exchange/network access. | Ops | Mitigated (design) — implemented Phase 2 |
| S6 | Local database (ledger, Freqtrade state) and `.env` are not encrypted at rest and the host is lost, stolen, or read by the hosting provider. | Low | Medium | **Mac:** FileVault (confirmed On 2026-09-09, `fdesetup status`). **VPS:** no customer-controlled at-rest encryption is available on Hetzner Cloud and LUKS would block unattended reboots (ADR-0011), so the control is *limiting what is on the disk*: the exchange key is trade-only, no withdrawal, IP-whitelisted; principal is $100; no secrets inside the ledger DB. | Ops | Accepted (ADR-0011, 2026-10-04) for the VPS; Mitigated for the Mac |
| S7 | **VPS compromise.** An attacker gains a shell on the VPS (stolen SSH key plus tailnet access, a container escape, a compromised Tailscale or Hetzner account, an unpatched vulnerability) and can read `.env` and drive Freqtrade. | Low | High | Zero public inbound ports (Hetzner firewall, external `nmap` verified); key-only SSH for one user; `fail2ban`; `unattended-upgrades`; passphrase-protected SSH key; exchange key has no withdrawal permission and is IP-whitelisted, so funds cannot leave the exchange account; loss limits (R4) halt trading independently; response is to revoke keys and rebuild from zero ([`rebuild-vps.md`](06-runbooks/rebuild-vps.md)) and rotate every secret ([`key-rotation.md`](06-runbooks/key-rotation.md)). Threat table in `04-architecture/security.md`. | Ops | Mitigated (design) — implemented Phase 3 (3A-0); residual: `deploy` is root-equivalent, Tailscale ACLs TBD (Phase 3) |
| S8 | **Public SSH reachable after `make vps-lockdown` (incident, 2026-10-04).** After lockdown (`bootstrap_ssh=false`, firewall with zero inbound rules) an `ssh` to the public IP was reported to succeed (exit 0), i.e. lockdown was not effective. | Low | High | Terraform state showed the firewall attached to the server (`apply_to.server`, `firewall_ids`) with no rules, so the "firewall not attached" theory was ruled out. **Root cause not confirmed**: re-tests from the operator's network at 2026-10-04 timed out on TCP 22. Candidate causes: (a) the zero-rule firewall not being enforced as documented, (b) an `ssh` multiplexed/proxied path. Fixes regardless of cause: lockdown firewall now carries an inert sentinel inbound rule (ICMP from 192.0.2.1/32) so it never depends on empty-means-drop; host layer `ufw` default-deny + allow only `tailscale0` and `ssh.socket` `ListenStream` = Tailscale IP + loopback (`scripts/harden-host.sh`, also run by cloud-init; Ubuntu 24.04 socket activation ignores `ListenAddress`); `make verify-lockdown` fails if TCP 22 on the public IP connects, run after every lockdown. Runbook: [`provision-vps.md`](06-runbooks/provision-vps.md). | Ops | Mitigated (design) — verify with `make verify-lockdown` + Hetzner API check after applying; root cause Open |
| S8 | **Terraform state-file leak.** `infra/terraform/terraform.tfstate` contains the rendered cloud-init, including the Tailscale auth key, and describes the server layout. If committed, pushed or synced, that secret is exposed. | Low | Medium | Local state only, no remote backend; `*.tfstate*` and `.terraform/` git-ignored at both the repo root and `infra/terraform/` (so `git add -A` skips them); gitleaks pre-commit hook; Tailscale key is single-use with 1-day expiry and revoked after first join, so a leaked copy is already dead; Terraform secrets are env vars only, never in tfvars. State file lives on the FileVault-encrypted Mac only; do not put it in iCloud/Dropbox folders. | Operator | Mitigated (design) — implemented Phase 3 (3A-0) |
